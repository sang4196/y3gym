## 실행 규칙

1. 현재 지침·작업 기록·담당 세션 상태·Git 변경을 확인한다. 현재 작업이 있으면 중복 지시/동시 쓰기를 하지 않는다.
2. 설계자는 다음 준비된 단위의 범위·기존 제안 중 채택할 기준·완료 조건을 개발노예에게 전달한다. 명세 안의 통상 구현 선택은 근거를 기록해 결정하며 매번 사용자 재승인을 요구하지 않는다.
3. 개발노예가 구현·전용 PostgreSQL test DB 검사·문서화·필요한 로컬 적용을 수행한다. 사용자 편집 DB·계정·미디어·기존 SPIKE는 보존하고 seed/초기화/자료 이관을 반복하지 않는다. 비파괴 migration과 필요한 운영자 역할 권한 확장은 허용하되 비밀번호는 바꾸지 않는다.
4. 실제 화면 확인이 필요한 경우에만 완료된 기능 단위의 핵심 시나리오를 묶어 요청한다. 사용자 수동 보고와 에이전트 직접 관찰을 구분하고 기존 성공 흐름을 새 결함 없이 반복하지 않는다. 화면 확인 대기는 가능한 독립 개발을 막지 않는다.
5. 개발 담당자가 쓰기를 멈춘 뒤 깃노예가 브랜치 비교·코드/문서/검증 근거·비밀파일 제외를 확인한다. 결함이 있으면 개발 담당자에게 돌려 수정 후 재검토한다.
6. 문제가 없으면 검토된 변경만 commit/정상 push하고 실제 원격과 작업 트리 상태를 확인한다. reset/clean/restore/stash/force push/임의 merge는 하지 않는다.
7. 설계자가 단위 결과·커밋·미검증을 짧게 보고하고 다음 준비 단위를 진행한다. 사용자가 답해야 하는 항목만 별도 대기시킨다.
