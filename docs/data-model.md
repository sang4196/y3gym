## 1. 문서의 지위와 범위

`docs/screens.md`의 확정 제품 기준을 보존한다. 그 문서의 화면 배치·공개 정책 제안이 파일에 저장되었다는 이유만으로 모두 확정된 것으로 취급하지 않는다. 본 문서에서 새로 정의하는 필드명, 저장 방식, 제약, 삭제 정책은 기술 설계 제안이다.

확정 요구와 제안이 충돌하면 확정 요구를 보존하고 충돌을 보고한다. 파일 생성 시각이 더 최신이라는 이유로 기존 사용자 결정을 덮어쓰지 않는다.

이 단계는 콘텐츠의 소유권·관계·공개 규칙을 정의한다. 실제 DB 엔진, 컬럼 길이, ORM 클래스, CMS 클래스 상속, 라이브러리 버전은 이후 Architecture ADR에서 확정한다. 아래의 논리 모델 수와 실제 DB 테이블 수는 같다고 가정하지 않는다.

## 2. 보존하는 제품 기준

- 하나의 공통 홍보·정보 제공 홈페이지다. 가격과 PT 운영관리 서비스 연계는 제외한다.
- 운영자는 정해진 구조의 콘텐츠를 편집한다. 자유로운 페이지 빌더는 제공하지 않는다.
- 본점과 지점은 같은 데이터 구조다. 하나를 본점으로 지정한다.
- 지점별 시설·이용안내·주소·연락처를 관리한다. 지점 공개 시 홈과 지점 안내에 자동 반영한다.
- 트레이너는 정확히 하나의 지점에 소속된다. 트레이너 소개는 지점별로 자동 구성한다.
- 직급은 선택 입력인 자유 텍스트다. 별도 직급 모델·메뉴·권한·자동 정렬 규칙을 만들지 않는다.
- 공지·이벤트·팝업은 공통이다. 이 세 콘텐츠에 지점 소유권을 추가하지 않는다.
- 게시글 작성·공개와 팝업 활성화는 독립이다. 팝업에는 사용 설정과 시작·종료 일시가 있다.
- 고객용 프론트 분리 후에도 같은 콘텐츠와 공개 규칙을 사용한다. 관리자 화면을 별도로 새로 개발하는 것을 전제로 하지 않는다.

## 3. 논리 모델과 관계

| 논리 모델 | 역할 | 연결 |
|---|---|---|
| SiteContent | 브랜드·홈 소개에 사용하는 공통 설정 한 묶음 | CMS 이미지 참조 |
| Branch | 본점과 지점의 소개·이용·상담·위치 정보 | 시설 사진 목록, 트레이너 목록 |
| BranchPhoto | 특정 지점의 시설 사진과 표시 순서 | Branch 하나에 소속 |
| Trainer | 트레이너의 공개 프로필 | Branch 하나를 필수 참조 |
| TrainerCareer | 약력의 개별 항목 | Trainer 하나에 소속 |
| Post | 공지사항·이벤트 게시글 | 선택적 팝업 설정 |
| Popup | 게시글을 일정 기간 홍보하는 설정 | Post 하나를 필수 참조 |

이미지 파일·변환본·운영자 계정·권한·편집 이력은 선택한 CMS의 기존 기능을 우선 재사용한다. 이를 위 표의 모델 수에 맞추기 위해 새 테이블로 재구현하지 않는다.

Branch : Trainer = 1 : N (확정). Branch : BranchPhoto = 1 : N (제안). Trainer : TrainerCareer = 1 : N (제안).

**Post : Popup = 1 : 0..1은 v1 단순화를 위한 추가 제안**이다. 게시글당 팝업 설정 하나를 재사용하는 안이며, 사용자가 최대 개수를 명시적으로 확정한 것은 아니다. Popup마다 게시글 하나가 반드시 있어야 한다. 지점과 Post/Popup 사이에는 관계를 추가하지 않는다.

## 4. 공통 데이터 원칙

식별자는 이름과 구분한다. 이름·직급·주소를 바꿔도 객체 식별자는 유지한다. 식별자 생성 방식과 DB 타입은 ADR에서 정하고, 공개 API에서는 불투명 문자열로 표현하는 안을 제안한다.

관리자용 생성·수정 시각과 수정자 등은 CMS 기능으로 충족되는지 먼저 확인한다. 공개 화면에 필요하지 않은 운영자 정보나 내부 경로는 API에 내보내지 않는다.

반복 항목의 `sort_order`는 작은 값이 먼저 오도록 제안한다. 같은 값에는 안정적인 식별자 정렬을 보조 기준으로 사용한다. 직급·이름으로 표시 순서를 추론하지 않는다.

선택 텍스트는 입력 시 앞뒤 공백을 정리하고, 공백뿐인 값은 미입력으로 취급한다. API에서는 미입력 단일 값은 `null`, 목록은 `[]`로 정규화한다.

### 4.1 저장·공개 반영 단위 — P-01 Proposed

Post만 공개본과 수정 초안을 분리한다. 그 외 모델은 단일 현재값과 공개 여부/기간으로 처리하며 수정 이력을 공개 대기 리비전으로 해석하지 않는다.

| 대상 | 저장 단위 | 새 공개 조회 반영 시점 |
|---|---|---|
| SiteContent | 공통 설정 한 묶음 | 유효한 저장 커밋 후 |
| Branch / BranchPhoto | 지점 필드·시설 사진 배치·이용안내 | 공개 지점의 유효한 부모 편집 저장 커밋 후 |
| Trainer / TrainerCareer | 소속·직급·사진 참조·한줄소개·약력 | 유효한 부모 편집 저장 커밋 후, 프로필과 지점 모두 공개일 때 |
| Post | 제목·분류·본문·본문 이미지 참조·대표 이미지 참조 | 새 버전 공개 커밋 후; 수정 초안 저장은 기존 공개본 유지 |
| Popup | 연결 글·문구·이미지 참조·기간·사용 여부 | 저장 커밋 후 후보 조회에서 공개 글·기간·사용 여부 재판정 |

Branch와 Trainer의 부모·하위 항목은 같은 DB 트랜잭션으로 저장하며 일부만 반영된 상태를 허용하지 않는다. 공개 현재값 변경은 저장 전 공개 검수를 한다. 새 지점·트레이너의 미완성 입력은 ‘비공개 준비 상태’이며 게시글식 수정 초안이 아니다. 기존 소개를 숨기고 수정하려면 먼저 비공개로 전환하고, 그동안 고객 화면에서도 사라짐을 안내한다.

이미지 바이너리 업로드는 DB 트랜잭션과 동일하지 않다. 부모 저장 실패 후 남은 미참조 자산은 미공개로 유지하고 업로드만으로 공개하지 않는다. 공개 조회는 커밋된 부모·하위 항목의 일관된 결과여야 하며 다중 쿼리 조회 중 동시 변경으로 구/신 항목이 혼합되지 않는지도 검증한다. 원자적 저장만으로 모든 조회의 일관성이 자동 보장된다고 가정하지 않는다.

### 6.1 공개·본점 규칙 — 제안

공개 지점만 고객 조회에 포함한다. 정렬은 본점 우선, 이후 `sort_order`, 동률에는 식별자를 사용한다.

P-02 Proposed: 최초 준비 중 공개 지점 0개·본점 0개를 허용하며 비공개 준비 지점은 여러 개일 수 있다. 첫 지점 공개와 본점 지정은 한 작업으로 처리한다. 공개 지점이 있으면 공개 본점은 정확히 하나이며 비공개 지점을 본점으로 지정하지 않는다. 현재 본점 비공개는 다른 공개 지점으로 본점 변경과 함께 수행한다. 운영 중 마지막 공개 지점을 비공개로 바꿔 0개로 만드는 일반 편집 작업은 차단한다. 전체 종료 기능은 추가하지 않는다.

본점 변경은 기존 본점 해제와 새 본점 지정을 하나의 원자적 작업으로 수행하고 동시 요청도 검증한다. **중복 방지 제약만으로 '반드시 하나 존재'까지 보장된다고 가정하지 않는다.** 존재 보장과 비공개·삭제 제한은 별도 저장 규칙으로 검증한다. DB별 구체 제약과 잠금 방식은 ADR에서 정한다.

P-01 Proposed: 본점·소속 변경에는 게시글식 수정 초안을 적용하지 않는다. 부모 편집 저장 트랜잭션에서 관계·본점 제약을 검증하고 실패하면 전체 변경을 되돌린다. P-02의 최초 0개와 운영 중 양수→0개 전환 차이는 모든 편집 경로와 동시 요청에서 지켜야 한다.

공개 전 지점명·기본 주소·전화 또는 카카오톡 중 하나 이상의 유효한 상담 경로를 요구하는 안을 제안한다. 이미지·이용안내의 필수 여부와 길이 제한은 상세 설계에서 정한다.

### 6.2 위치 일관성 — 제안

위치 논리 상태는 `unverified`, `confirmed`, `failed`로 구분한다. 현재 기본 주소에 대해 위치를 찾고 운영자가 확인했을 때만 `confirmed`로 취급한다.

위치를 확인한 주소와 현재 주소의 일치 여부를 관리한다. 기본 주소가 변경되면 이전 위치 확인을 무효화하고 공개 마커를 `null`로 바꾼다. 이전 주소로 시작한 조회가 늦게 완료되어도 새 주소의 좌표로 덮어쓰지 않도록 요청 기준 주소를 재검증한다.

확인된 좌표가 없더라도 주소·연락처는 제공하고 잘못된 마커는 숨긴다. 지도 요청 실패를 지점 정보 전체 삭제나 임의 좌표 표시로 처리하지 않는다.

좌표 캐시·장기 저장·표시 방식은 지도 제공자의 해당 정책과 쿼터를 검증한 뒤 확정한다. 이 논리 모델은 특정 제공자의 결과를 무기한 저장해도 된다는 뜻이 아니다. 지도 REST 비밀키나 원본 내부 오류를 공개 API에 포함하지 않는다.

## 7. BranchPhoto — 시설 사진

항목은 `branch`, `image`, `caption`, `alt`, `sort_order`다. 사진 파일은 CMS 이미지 자산을 참조한다. 운영자는 지점 편집 안에서 여러 장을 추가하고 순서를 조정한다.

시설 사진의 공개 여부는 부모 지점의 공개 상태를 따른다. 사진 행 삭제는 해당 지점의 배치 제거이며, 여러 곳에서 쓰는 원본 이미지 파일의 삭제와 동일시하지 않는다.

P-01 Proposed: 사진 배치·순서 변경은 지점 편집 트랜잭션 안에서 저장한다. 다른 지점의 사진 행을 요청에 섞어 넣어도 수정할 수 없도록 부모 소유권을 검증한다. 정렬은 §4를 따른다. 공유 이미지라도 배치·캡션·대체 설명은 사용처별로 관리한다.

대체 설명은 사진의 사용 맥락에 맞춰 관리한다. 의미 있는 시설 사진에는 공개 검수 시 적절한 설명을 확인한다.

## 8. Trainer / TrainerCareer — 트레이너와 약력

### 8.1 Trainer

| 항목 | 의미 |
|---|---|
| id / branch | 식별자 / 소속 지점 하나를 필수 참조 |
| name | 표시 이름 |
| job_title | 선택 자유 텍스트 직급 |
| profile_image | 프로필 사진과 대체 설명 |
| short_intro | 한줄소개 |
| publication | 프로필 자체의 공개 상태 |
| sort_order | 지점 내 표시 순서 |

프로필 자체가 공개이며 소속 지점도 공개일 때만 공개 조회에 포함한다. 지점이 비공개라고 트레이너의 자체 공개 설정이나 데이터를 변경하지 않는다. 빈 지점 섹션은 출력하지 않는다.

소속 변경은 같은 Trainer의 지점 참조를 변경한다. 사진·약력을 복제하거나 새 트레이너 객체를 만들지 않는다. P-01 Proposed에 따라 약력 등과 함께 저장 커밋 후 새 공개 지점 섹션으로 이동한다. 새 소속이 비공개이면 고객 조회에서 제외하되 자체 공개 상태는 유지한다. 공개 지점의 첫 유효 공개 프로필은 섹션을 자동 생성하며 별도 배치 데이터가 없다.

공개 전 이름·소속 지점·프로필 사진·한줄소개를 요구하는 안을 제안한다. 사진이 없는 ‘비공개 준비 상태’ 저장은 허용한다(P-01 Proposed). 직급과 약력은 선택 입력이며 실제 확인된 내용만 공개한다.

### 8.2 TrainerCareer

항목은 `trainer`, `category`, `text`, `sort_order`다. `category`는 고정된 `education`, `award`, `certification`, `experience` 중 하나다. 별도 분류 관리 화면을 제공하지 않는다.

편집 화면은 트레이너 안의 약력 목록으로 구성한다. 각 항목은 짧은 텍스트로 관리하고, 항목이 없는 구분은 API와 화면에서 생략한다. 분류 순서는 위 고정 순서, 분류 안에서는 `sort_order` 순을 제안한다.

별도 반복 관계 모델을 사용할지 CMS의 제한된 반복 필드로 저장할지는 ADR에서 선택한다. 선택 결과와 무관하게 공개 API의 약력 구조는 동일하게 유지한다.

## 9. Post — 공지·이벤트

항목은 `id`, `category(notice/event)`, `title`, `cover_image`, `body`, `publication`, `first_published_at`, `updated_at`이다. 지점 참조, 가격, 댓글·좋아요·태그를 추가하지 않는다.

`body`는 서식·이미지를 지원하는 CMS 본문으로 관리하되 전체 홈페이지 HTML이나 임의 스크립트를 입력하는 필드로 만들지 않는다. 공개 DTO의 `updated_at`은 마지막으로 공개된 내용의 갱신 시각이다. 관리자 초안 저장 시각과 별도 의미이며 CMS 시각 필드와의 정확한 매핑은 ADR에서 정한다.

### 9.1 저장과 공개 — 제안

P-01 Proposed: Post만 초안 저장, 공개, 공개 철회를 구분한다. 이미 공개된 글에 수정 초안을 저장해도 제목·본문·이미지 참조·공개 시각·팝업이 사용하는 게시글 제목은 기존 공개본을 유지하고 새 버전 공개 시만 바뀐다. 공개 본문이 별도 초안 객체를 동적으로 참조하여 바뀌는 임베드는 추가하지 않는다. 다단계 승인·예약 게시글 공개는 추가하지 않는다.

CMS를 채택하면 기존 리비전·공개 기능을 우선 활용한다. `status`, `is_published`, `live` 등을 독립된 진실의 원천으로 중복 운영하지 않는다. 아래 상태는 논리적 의미이며 반드시 새 enum 컬럼을 만들라는 뜻이 아니다.

| 동작 | 공개 조회 결과 |
|---|---|
| 신규 초안 저장 | 목록 제외, 상세 404 |
| 최초 공개 | 공개본 제공, 최초 공개 시각 기록 |
| 공개된 글에 수정 초안 저장 | 기존 공개본 유지 |
| 수정본 공개 | 새 공개본 제공 |
| 비공개 전환 | 목록 제외, 상세 404, 연결 팝업 제외 |
| 다시 공개 | 공개본 제공 |

최초 공개일은 일반 수정·재공개로 자동 갱신하지 않고, 목록을 `first_published_at` 내림차순으로 정렬하는 안을 제안한다. 이 공개일 정책은 아직 사용자 확정이 아니다. 예약 게시글 공개는 추가하지 않는다.

C-01 보정: 본문·이미지·팝업을 포함한 모든 공개 콘텐츠의 가격을 공개 전에 사람이 검수한다. 전용 가격 필드 부재만으로 검수 완료가 아니며 자동 OCR·가격 판별은 추가하지 않는다.

## 10. Popup — 기간제 홍보

| 항목 | 의미 |
|---|---|
| id / post | 식별자 / 연결 게시글 하나 |
| title / message / image | 표시 제목·문구·선택 이미지 |
| enabled | 기본 false인 사용 설정 |
| starts_at / ends_at | 시작·종료 일시 |
| priority | 후보 정렬 기준. 작은 값 우선 제안 |

v1 게시글당 설정 하나는 §3의 추가 제안이다. 팝업 작성·비활성 저장 시 미완성 기간을 허용할 수 있지만, 활성화 시 비어 있지 않은 제목, 문구 또는 이미지 중 최소 하나, 시작·종료를 모두 검증한다. 시작과 종료가 모두 있을 때는 항상 시작보다 종료가 늦어야 한다.

P-01 Proposed: 팝업은 연결 글·문구·이미지 참조·기간·사용 여부를 함께 저장하는 현재 설정이다. 수정 초안이나 독립 공개본은 없으며 사용 중 저장도 이후 후보 조회에 반영된다. 게시글 수정 초안은 연결된 공개 게시글의 제목을 바꾸지 않는다.

공개 후보 판정은 다음과 같다. 비교용 현재 시각은 한 요청에서 한 번 정한다.

```text
post has a publicly available version
AND popup.enabled
AND popup.starts_at <= now < popup.ends_at
```

입력·표시는 Asia/Seoul, 내부 비교는 시간대가 명확한 시각으로 한다. 현재 노출 가능/예약/종료는 계산 결과이지 별도 배치가 계속 수정하는 중복 상태값이 아니다.

팝업 기간 종료·비활성화는 게시글 상태를 변경하지 않는다. 게시글 비공개는 다음 공개 조회부터 팝업도 제외한다. 이미 열린 브라우저 화면을 원격 회수하는 기능은 추가하지 않는다.

여러 후보의 정렬은 `docs/api-contract.md` §5, 방문자별 닫기는 §6의 제안에 따른다. 사용자의 숨김 기록을 서버의 고객 계정·프로필로 저장하지 않는다.

## 11. 삭제·이미지 처리 — P-03~04 Proposed

### 11.1 영구 삭제·교체·복원 — P-03 Proposed

일반 콘텐츠 운영자에게 지점·트레이너·게시글·팝업·원본 이미지 영구 삭제 권한을 제공하지 않는다. 메뉴 숨김뿐 아니라 직접 요청도 서버 권한에서 차단한다. 일상 운영은 본점 제약을 지킨 비공개·팝업 비활성화로 처리한다. 시설 사진 배치 제거·약력 한 줄 제거는 부모 편집이며 허용한다.

이미지의 시각적 내용 교체는 새 자산 업로드와 부모 참조 변경으로 처리한다. 기존 자산 ID·URL의 바이너리를 덮어쓰지 않는다. 공개본·수정 초안·보존 리비전이 참조하는 원본을 유지하며, 사용처의 캡션·대체 설명을 공유 원본 변경과 구분한다.

유지보수 영구 삭제는 별도 승인 작업이다. 공개본·현재 비공개 객체·수정 초안·보존된 모든 리비전의 참조를 검사한다. CMS 참조 인덱스가 이 범위를 모두 처리한다고 가정하지 않는다. 본점·트레이너가 연결된 지점, 팝업이 연결된 게시글은 선행 관계 정리 없이 삭제하지 않는다. 비공개 트레이너도 검사한다. 허용된 부모 삭제 때만 부모 전용 사진 배치·약력을 정리하고 공유 원본을 연쇄 삭제하지 않는다. 자동 미참조 삭제·리비전 청소·일괄 삭제 화면은 추가하지 않는다.

CMS의 Post 과거 리비전 복원을 제공한다면 먼저 수정 초안으로 복원하고, 이미지 존재·관계 유효성·공개 가능성을 검수한 뒤 별도로 공개한다. 필수 이미지가 없으면 새 공개를 막고 가짜 경로·임의 사진을 쓰지 않는다. 스토리지 유실은 오류 보고·백업 복구 대상이다. 다른 모델의 신규 범용 복원 기능은 추가하지 않는다. 이 제안은 최고 권한·DB 직접 조작까지 차단한다는 보장이 아니다.

### 11.2 이미지 접근 — P-04 Proposed

한 번도 공개하지 않은 파일은 URL을 알아도 무권한으로 볼 수 없게 하는 안이다. 업로드 원본은 비공개 저장소 또는 직접 서빙되지 않는 경로에 두며, 원본·관리자 썸네일·미공개 변환본은 인증된 관리 경로에서 권한을 확인한다. 공개 API에 관리자 세션이 붙어도 범위를 넓히지 않는다. 무작위 파일명은 접근 제어가 아니다.

일반 방문자는 현재 공개 사용처가 있는 표시용 변환본만 조회한다. 공개 사용처 판정은 SiteContent의 유효한 저장값, 공개 Branch와 사진 배치, 프로필·지점 모두 공개인 Trainer, Post 실제 공개본, 기간·사용 설정·연결 공개 글을 만족하는 Popup을 따른다. 수정 초안·과거 리비전 참조만으로는 공개 사용처가 되지 않는다.

공유 이미지에 공개 사용처가 하나라도 있으면 그 공개 표시본은 조회 가능하다. 미공개 독점 자료는 새 자산을 사용한다. 마지막 공개 사용처가 사라지면 이후 원본 서버의 무권한 조회에서 표시본을 제공하지 않는다. 방문자·외부 캐시의 과거 공개 복사본과 다운로드 회수는 보장하지 않는다.

미리보기·보호 이미지 응답은 캐시하지 않는다. 공개 표시본의 캐시는 별도 결정하되 장기 공개 CDN 캐시는 자동 도입하지 않는다. 웹 서버 직접 경로·객체 저장소 URL·원본·썸네일·변환본의 우회 접근을 모두 검증한다. 보호 전달 경로·서명 URL·내부 전달 방식은 ADR-0002 기술 검증 후 결정한다. Wagtail 기본 이미지 권한만으로 완성된다고 가정하지 않는다.

## 12. 구현 경계와 기술 근거

고객 화면은 공개 조회 결과를 사용하고, 관리자는 선택한 CMS에서 콘텐츠를 편집한다. 초기 템플릿과 미래 공개 API가 공통 공개 조회 로직을 호출하도록 제안한다. 초기 템플릿이 자기 서버 API를 HTTP로 재호출할 필요는 없다.

Django + Wagtail + PostgreSQL은 A-01 Proposed이며 채택·설치 사실이 아니다. Wagtail의 기존 관리 화면과 반복 하위 편집을 우선 활용하고, P-01에서는 Post에만 공개본/초안 기능 적용을 권고한다. RevisionMixin/DraftStateMixin 조합 등 실제 클래스와 원자성·권한 연동은 최소 검증 후 ADR로 정한다. [S1]

현재 개발 실행·가상환경·테스트는 Windows 호스트 위 WSL Ubuntu 기준이다(2026-09-18 갱신). Windows는 편집·브라우저 접근 환경이며 별도 Linux 상용 서버의 배포판·버전·호스팅·실행 방식은 TBD다. 개발/운영 DB·미디어·비밀값을 분리하고 PostgreSQL에서 관계·동시성을 검증하는 안을 제안한다. OS 간 가상환경을 복사하지 않으며 운영 HTTPS·로컬 HTTP 예외, 시간대·경로·배포·복원은 ADR-0001의 ENV-01~06으로 추적한다. 승인된 SPIKE-01의 로컬 SQLite 시험은 PostgreSQL 검증이나 정책 승인이 아니다.

Wagtail 공식 문서는 Headless 구성과 REST API 사용을 지원하지만, 별도 프론트 미리보기·본문 이미지/링크에는 연동 고려사항이 있다. 이 계약은 프론트 분리 시 작업이 전혀 없다는 약속이 아니다. [S2]
