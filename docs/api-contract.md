변경 요약 (2026-09-18): C-01~05의 검증 전제를 보정하고 P-01~04 Proposed의 모델별 반영·미디어 경계 및 A-01의 운영 HTTPS/로컬 HTTP 예외를 연결했다. API-01~18을 보존하고 API-19~24를 추가했다. 정책 문서화는 승인이나 구현 완료가 아니다. RV/ENV의 비API 계층 검증은 두 ADR에서 추적한다.

> 이 문서는 향후 분리될 고객용 프론트가 사용할 데이터 계약의 초안이다. API가 이미 구현되었다거나 현재 HTTP 엔드포인트를 반드시 모두 개발해야 한다는 뜻이 아니다. 경로·필드·응답 방식은 제안이며, 실제 구현은 Architecture ADR과 별도 작업 승인 후 진행한다.

## 1. API의 경계

고객에게 이미 공개하기로 한 콘텐츠의 **조회 전용** API다. 회원가입, 고객 로그인, 예약·결제, PT 관리, 트레이너 업무 계정, 관리자용 공개 CRUD API는 추가하지 않는다.

운영자 편집은 선택한 CMS 관리 화면에 남긴다. 관리자 세션이 붙어 있더라도 공개 API가 초안·비공개 데이터를 추가로 반환하지 않는다. 미리보기는 별도 권한 있는 관리 흐름이다.

`/api/v1/`은 프로젝트의 공개 계약 버전이다. Wagtail 등의 내장 API 버전 번호와 동일하다는 뜻이 아니고, 아래 경로가 CMS 설치만으로 자동 생성된다는 뜻도 아니다.

초기 Django 템플릿과 향후 API는 공통 공개 조회 함수와 출력 변환을 재사용하는 A-01 Proposed다. Django + Wagtail + PostgreSQL 채택은 미정이며, 템플릿이 자기 서버 API를 HTTP로 재호출하는 구조는 요구하지 않는다.

## 2. 공통 규칙 — 제안

| 항목 | 계약 |
|---|---|
| 콘텐츠 읽기 | GET. HEAD/OPTIONS는 선택 프레임워크의 허용 정책에 맞춤 |
| 쓰기 요청 | 아래 공개 경로에서 지원하지 않음; POST/PUT/PATCH/DELETE는 405 |
| 출력 | JSON, UTF-8 |
| ID | 불투명 문자열. 프론트는 숫자 크기·이름·접두어 의미를 해석하지 않음 |
| 시각 | ISO 8601, UTC `Z`를 기본 출력. 관리·오늘 숨김 기준은 Asia/Seoul |
| 누락 값 | 선택 단일 값은 null, 반복 값은 [] |
| 데이터 없음 | 정상 목록은 200과 빈 items |
| 비공개 상세 | 미존재와 같은 404; 초안 존재 여부·내부 상태를 노출하지 않음 |
| 잘못된 질의 | 400과 정해진 오류 구조 |
| 서버 시각 | 성공 응답 meta.server_time에 판정 시각을 포함 |
| 정렬 | 서버가 정해진 순서로 반환; 프론트가 직급 등으로 재정렬하지 않음 |

### 2.1 공통 응답

단일 객체는 `data`, 목록은 `items`를 사용한다. 게시글 목록만 `pagination`을 추가한다. 응답 스키마에서 문서화한 필드를 항상 유지하고 비어 있는 선택 값은 null로 표현한다.

```json
{
  "items": [],
  "meta": {
    "server_time": "2026-10-01T00:00:00Z"
  }
}
```

오류 예시는 계약용 예시다.

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "콘텐츠를 찾을 수 없습니다."
  }
}
```

400은 `INVALID_QUERY`, 405는 `METHOD_NOT_ALLOWED`, 의존 서비스 등을 포함한 내부 실패는 공개용 일반 오류로 처리한다. 운영자 이름, 디버그 traceback, 키, SQL, 내부 파일 경로를 응답에 넣지 않는다.

### 2.2 이미지·전화·링크

Image는 `{url: string, alt: string, width: integer, height: integer}` 구조를 제안한다. 선택 이미지 미등록은 객체 전체가 null이며 필수 이미지가 없는 새 공개는 차단한다(P-03 Proposed). url은 분리된 프론트에서도 사용 가능한 절대 주소로 출력한다. A-01 Proposed에서 운영은 HTTPS만 허용하고 로컬 개발만 명시된 개발 오리진의 HTTP를 허용한다. 이 예외를 운영에 적용하거나 Windows 로컬 파일 경로를 URL로 반환하지 않는다(ENV-02·05). 실제 접근 URL을 만들 수 없는 이미지를 가짜 경로로 대체하지 않는다.

P-04 Proposed: API는 현재 공개 사용처가 허용하는 표시용 이미지 URL만 출력하며 원본·관리자 썸네일·초안 전용 변환본·스토리지 내부 경로를 반환하지 않는다. 관리자 미리보기는 별도 인증된 경로로 제공한다. URL 미반환 검사만으로 파일 보호를 통과 처리하지 않고 원본 서버·스토리지 직접 접근까지 ADR-0002의 RV-08~10으로 검증한다.

의미 있는 이미지의 대체 설명을 공개 검수한다. 의도된 장식 이미지는 빈 alt를 허용한다. 서빙 크기·비율·여러 해상도 제공은 화면/미디어 ADR에서 정한다.

지점의 `phone`은 `{display: string, href: string}` 또는 null이다. display는 읽기 쉬운 번호, href는 검증된 `tel:` 링크다. 카카오톡 주소는 관리자에서 검증한 채널 URL 또는 null이다. `javascript:` 등 실행 스킴이나 임의 외부 리다이렉트를 허용하지 않는다.

API의 프론트 링크는 고정 UI 경로 제안을 사용하되 안정적인 ID로 생성한다. 예: `/branches/#branch-{id}`, `/trainers/#branch-{id}`, `/posts/{id}/`. 이름 변경으로 앵커가 바뀌지 않도록 한다. 실제 라우팅은 별도 승인 시 동기화한다.

## 3. 엔드포인트 목록 — 제안

| GET 경로 | 목적 | 응답 |
|---|---|---|
| `/api/v1/site/` | 공통 브랜드·홈 콘텐츠 | data: SiteContentDTO |
| `/api/v1/branches/` | 공개 지점과 시설·이용안내 | items: BranchDTO[] |
| `/api/v1/trainer-sections/` | 지점별 공개 트레이너 | items: TrainerSectionDTO[] |
| `/api/v1/posts/` | 공지·이벤트 공개 목록 | items: PostSummaryDTO[], pagination |
| `/api/v1/posts/{id}/` | 공개 게시글 상세 | data: PostDetailDTO |
| `/api/v1/popups/active/` | 현재 공개 가능한 팝업 후보 | items: PopupDTO[] |

지점·트레이너는 소규모 소개 목록이므로 v1에서 전체 공개 목록을 반환하는 안이다. 일부를 잘라내는 숨은 상한을 넣지 않는다. 지점/트레이너 수가 크게 늘어 페이지 분할이 필요해지면 별도 계약을 검토한다. 지점별 게시글 필터나 게시판은 추가하지 않는다.

## 4. 데이터 계약

아래는 각 DTO의 전체 v0.2 제안이다. 필드 뒤 `?`는 객체가 아니라 그 값이 null일 수 있음을 뜻한다. 구현용 프로그래밍 언어 문법은 아니다.

### 4.1 SiteContentDTO

| 필드 | 타입 |
|---|---|
| brand_name | string |
| logo | Image? |
| hero_title / hero_description | string? |
| hero_image | Image? |
| introduction | string? |
| introduction_image | Image? |

지점·트레이너·최근 글 목록을 여기의 독립 편집 데이터로 복제하지 않는다. 홈은 branches 조회와 posts의 첫 페이지 조회를 재사용한다. 필수 brand_name 등 사이트 설정이 준비되지 않았다면 `/site/`는 503과 `CONTENT_NOT_READY`를 반환하는 안을 제안한다. 준비된 설정의 선택 항목만 null로 반환하며 실제 사이트 공개 전 필수 콘텐츠를 검수한다.

P-01 Proposed: SiteContent는 별도 수정 초안 없이 유효한 저장 커밋 후 새 조회에 반영한다.

### 4.2 BranchDTO

| 필드 | 타입과 설명 |
|---|---|
| id / name | string / string |
| is_main | boolean |
| summary / cover_image | string? / Image? |
| address / address_detail | string / string? |
| phone / kakao_channel_url | Phone? / string? |
| business_hours / closed_days | string? / string? |
| parking_info / usage_notes | string? / string? |
| location | `{latitude: number, longitude: number}` 또는 null |
| facility_photos | `{image: Image, caption: string?}`[] |
| trainer_section_path | string?; 해당 지점 공개 트레이너가 있을 때만 경로 제공 |

공개 지점만 포함하고 본점 우선·설정 순서로 반환한다. 지도 상태의 원본 오류나 내부 검증용 주소는 반환하지 않는다. 현재 주소와 일치하는 확인된 위치만 location으로 제공한다. 검증 실패·주소 변경 직후에는 null이다.

P-01 Proposed: BranchDTO는 지점·시설 사진 배치·이용안내의 일관된 부모 저장 결과를 반환한다. 일부 하위 항목만 저장되거나 동시 조회에서 구/신 항목이 혼합되지 않도록 DB·조회 계층도 검증한다. facility_photos는 부모 지점의 배치만 포함하며 sort_order, 동률 ID 순으로 반환한다. P-02 Proposed의 최초 0개 상태는 빈 목록이지만, 운영 중 마지막 공개 지점 비공개는 관리자 저장에서 차단해야 한다. 공개 GET이 이 변경 제약을 집행하는 것은 아니다.

좌표 형식은 위도·경도를 명명하여 제공하고, 특정 지도 SDK의 x/y 배열 순서에 API를 결합하지 않는다. 실제 좌표계는 지리 좌표로 정규화하는 안이며 제공자 지원과 저장 정책을 ADR에서 검증한다.

### 4.3 TrainerSectionDTO / TrainerDTO

TrainerSectionDTO는 `{branch: BranchSummaryDTO, trainers: TrainerDTO[]}`다. BranchSummaryDTO는 `{id, name, is_main, page_path}`다. page_path는 해당 지점 안내 앵커다.

TrainerDTO 필드는 다음과 같다.

| 필드 | 타입 |
|---|---|
| id / name | string / string |
| job_title | string? |
| profile_image | Image |
| short_intro | string |
| career_groups | `{category: string, items: string[]}`[] |

category는 `education`, `award`, `certification`, `experience` 중 하나다. 빈 분류는 career_groups에서 생략하고 약력이 전혀 없으면 []다. 미입력 job_title은 null이다.

지점과 트레이너 모두 공개인 경우만 포함한다. 공개 트레이너가 없는 지점 섹션을 반환하지 않는다. 지점은 본점 우선·설정 순서, 프로필은 지점 내 설정 순서다. 직급에 의한 권한·정렬은 없다.

그룹화는 조회 결과다. 별도의 '트레이너 섹션 테이블'이나 운영자 배치 입력을 만들지 않는다.

P-01 Proposed: 소속·직급·사진 참조·한줄소개·약력은 같은 부모 저장 결과다. 공개 필수 조건을 충족하고 프로필·지점 모두 공개인 첫 트레이너는 섹션을 자동 생성한다. 소속 변경 후 동일 ID는 새 공개 소속에만 나타나며 새 지점이 비공개이면 제외한다. 직급 변경만으로 응답 정렬이나 관리자 권한을 바꾸지 않는다.

### 4.4 PostSummaryDTO / PostDetailDTO

PostSummaryDTO는 `id: string`, `category: notice|event`, `title: string`, `cover_image: Image?`, `published_at: datetime`, `detail_path: string`이다.

PostDetailDTO는 요약 필드에 `body_html: string`, `updated_at: datetime`을 추가한다. `published_at`은 데이터 모델의 최초 공개 시각을 사용한다는 제안이다. updated_at은 마지막 공개 내용 갱신 시각이며, 비공개 수정 초안의 저장 시각을 뜻하지 않는다.

공개본만 사용하고 초안 내부 직렬화·CMS 편집용 JSON은 반환하지 않는다. 일반 방문자에게 안전하게 표시할 수 있도록 허용한 서식으로 변환한 HTML을 제안한다. 자의적인 script·인라인 이벤트 핸들러·위험한 링크 스킴을 허용하지 않는다.

P-01 Proposed: Post만 공개본과 수정 초안을 분리하며 제목·분류·본문·본문/대표 이미지 참조를 한 공개 버전에서 읽는다. 수정 초안 저장은 공개 시각·팝업의 게시글 제목도 바꾸지 않는다. 별도 초안 객체의 동적 임베드로 공개본이 우회 변경되는 기능은 추가하지 않는다. P-03 Proposed의 과거 리비전 복원은 수정 초안으로 먼저 복원하고 재검증·공개 전에는 공개 API에 반영하지 않는다.

CMS 이미지 참조는 실제 공개 가능한 이미지 HTML로 변환하고, 본문 내부 링크는 고객용 프론트 경로로 해석되도록 한다. 저장된 CMS 전용 태그를 그대로 보내지 않는다. Wagtail Headless 문서는 본문·이미지·링크 표현의 연동 고려사항을 설명한다. [S1]

이미지/간단한 서식을 위한 CMS 기능을 우선 활용하되, 선택 버전의 기본 동작만 믿지 말고 출력 예제와 악성 태그 테스트로 확인한다. 자유로운 전체 페이지 HTML 편집기는 추가하지 않는다.

### 4.5 게시글 질의·페이지 분할

`category`는 생략 시 전체, `notice`, `event`만 허용한다. `page`는 기본 1인 양의 정수, `page_size`는 기본 10·최대 50으로 제안한다. 범위 밖 값이나 잘못된 category는 400이다. 화면에서 필터를 바꾸면 page=1로 시작한다.

정렬은 최초 공개 시각 내림차순, 동률에는 안정적인 식별자 역순이다. 정렬의 실제 DB 표현은 ADR에서 정한다. 관리·비공개 글은 total에도 포함하지 않는다.

pagination은 `{page, page_size, total, has_next}`다. 마지막 페이지를 넘는 유효한 page에는 200과 빈 items, 정확한 total·has_next=false를 반환한다.

아래는 실제 게시글이 없는 상황의 예시이며 운영 데이터를 뜻하지 않는다.

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "page_size": 10,
    "total": 0,
    "has_next": false
  },
  "meta": {
    "server_time": "2026-10-01T00:00:00Z"
  }
}
```

## 5. PopupDTO와 서버 판정

PopupDTO 필드는 `id: string`, `title: string`, `message: string?`, `image: Image?`, `starts_at: datetime`, `ends_at: datetime`, `post: {id: string, title: string, detail_path: string}`다. 게시글 title은 공개본의 제목을 사용한다.

P-01 Proposed: 팝업의 문구·이미지 참조·연결 글·기간·사용 여부는 수정 초안 없이 함께 저장하는 현재 설정이다. 유효한 저장 커밋 후 새 후보 조회에 반영한다. 팝업 자체 문구 저장과 연결 Post 수정 초안 저장을 혼동하지 않는다.

연결 글 공개 AND 사용 설정 활성 AND 시작 <= 판정 시각 < 종료를 만족하는 후보만 반환한다. 본문 전체, 비공개 예약 팝업, 내부 우선순위 필드를 프론트에 모두 공개해서 숨기게 만들지 않는다.

후보는 priority 오름차순, 시작 시각 내림차순, 안정적인 ID 순으로 정렬하는 안을 제안한다. 반환 순서 자체가 우선순위다. **여러 후보를 반환하는 것과 화면에 여러 개를 동시에 표시하는 것은 다르다.**

후보가 없으면 200과 빈 items다. 지도나 카카오톡과의 외부 연동 실패 때문에 이 API의 정상 결과를 빈 목록으로 위장하지 않는다. 실제 서버 실패는 오류 상태로 구분한다.

## 6. 팝업 프론트 동작 — 미확정 제안

`docs/screens.md`의 제안을 구체화한 다음 정책은 별도 승인이 필요하다.

1. 홈에서만 자동 노출한다. 새 탭 방문 세션에서 팝업을 아직 자동 표시하지 않았을 때만 후보를 검토한다.
2. 서버의 후보 순서에서 브라우저의 '오늘 숨김' 대상이 아닌 첫 항목을 선택한다. 선택 후보의 종료 시각이 이미 지났다면 표시하지 않는다. 표시 직전 필요 시 서버를 재조회한다.
3. 실제로 표시했을 때 탭 세션의 '자동 표시함' 상태를 기록한다. 해당 연속 방문에서는 최대 한 번만 표시하고, 닫았다고 다음 후보를 이어서 띄우지 않는다.
4. 일반 닫기는 같은 탭의 연속 탐색 중 재노출하지 않는다. '오늘 하루 보지 않기'는 해당 팝업 ID에 대해 한국 시간 다음 날 00:00까지 브라우저 저장소에 기록한다. 저장을 지원하지 않는 환경에서도 닫기는 정상 작동해야 한다.
5. 모든 후보가 숨김 대상이면 표시하지 않는다. 같은 팝업 문구 수정만으로 방문자의 당일 숨김을 초기화하지 않는다.

서버는 시간·공개 여부를 최종 판단한다. 브라우저의 숨김은 공개 가능한 후보를 추가로 줄이는 UX 규칙이며 인증·인가의 대체가 아니다.

API의 server_time으로 클라이언트의 시간 오차를 고려할 수 있으나, 프론트 분리·정적 빌드 캐시가 오래된 후보를 영구 보관하도록 만들지 않는다. 이미 열려 있는 화면을 관리자가 실시간 회수하는 기능은 범위 밖이다.

## 7. 공개 반영·캐시·연동 경계 — 제안

초기 콘텐츠 JSON 응답은 `Cache-Control: no-store`를 기본으로 제안한다. API와 서버 HTML 조회에 별도 장기 캐시를 두지 않고, 모델별 공개 반영 커밋 이후 시작된 새 요청은 최신 공개 상태를 조회하도록 한다. P-01 Proposed에서 SiteContent/Branch/Trainer는 유효한 현재값 저장, Post는 버전 공개·공개 철회, Popup은 설정 저장과 조회 시각 판정이 기준이다. Post 수정 초안 저장은 공개 반영이 아니다. 이미지 캐시는 아래 P-04와 ADR-0002에서 별도로 다룬다.

이후 캐시를 도입하면 게시글 비공개·지점 변경의 무효화와 팝업 시작/종료 경계를 함께 검증한다. 팝업 후보가 없는 응답의 캐시도 다음 시작 시각을 넘기지 않아야 한다. 정적 빌드 시 받은 후보를 그대로 배포해서는 안 된다.

특정 브라우저의 기존 화면·진행 중 요청을 원격 회수하는 보장은 하지 않는다. P-04 Proposed에 따라 공개 사용처가 모두 사라진 표시본은 이후 원본 서버의 무권한 새 조회에서 제공하지 않는다. 공개 사용처가 남은 공유 표시본은 계속 제공할 수 있다. 이미 내려받은 파일·방문자 및 외부 캐시에 남은 과거 공개 복사본의 회수는 보장하지 않는다. 미리보기·보호 이미지 응답은 no-store이며 장기 공개 CDN 캐시는 자동 도입하지 않는다. 서명만 유효하면 공개 철회 뒤에도 조회되는 전달 방식은 이 제안의 즉시 접근 판정을 충족하는지 별도로 검증한다.

프론트 분리 시 허용 오리진, CMS 관리자 세션·CSRF, 미리보기 권한, 미디어 도메인, 배포 반영 방식을 ADR로 검증한다. 공개 GET에 고객 JWT를 도입하지 않고, 관리자 비밀 정보를 고객 앱으로 옮기지 않는다.

지도 REST 키는 서버 관리다. 브라우저 지도 SDK가 요구하는 공개 식별 키는 제공자 정책에 따라 도메인 제한 등을 설정한다. SDK 종류와 키 구성을 이 문서로 확정하지 않는다.

## 9. 승인 전에 정할 것

API 경로·페이지 크기·정렬, 데이터 모델의 필수 공개 항목, 본문 출력 형식, 게시글당 팝업 개수, 후보 선택·닫기 정책은 본 초안의 제안이다. CMS/DB/프론트 종류·버전과 지도·미디어·배포 구현은 ADR에서 정한다.

자동으로 API 서버·관리자 프론트·OpenAPI 파일을 생성하거나 프로젝트 의존성을 설치하지 않는다. 문서 검토 결과와 승인된 범위를 바탕으로 별도 구현 작업을 정의한다.
