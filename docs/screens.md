## 1. 확정된 제품 기준

- 하나의 헬스장 공식 홈페이지로 소개·정보 제공·홍보를 통한 고객 유치를 목표로 한다.
- 고객 문의는 전화 또는 카카오톡 채널로 연결한다. 자체 상담 접수·예약·결제 기능은 현재 범위에 포함하지 않는다.
- 가격·요금 정보는 공개하지 않는다. 전용 가격 필드나 가격 안내 화면을 만들지 않는다.
- PT 운영관리 서비스와는 절대 연계하지 않는다. 고객·트레이너의 운영 서비스용 계정이나 수업 관리 기능을 추가하지 않는다.
- 현재 본점 한 곳이지만 여러 지점을 등록할 수 있다. 본점과 지점은 동일한 구조로 관리하고 하나를 본점으로 지정한다.
- 운영자가 지점을 등록·공개하면 기존 지점 소개 영역에 개발자 수정·재배포 없이 반영된다.
- 지점별 위치·연락처·지도·시설·이용안내를 관리한다. 공지·이벤트·팝업은 홈페이지 전체 공통이다.
- 지점 주소를 입력하면 외부 지도 서비스와 연동하여 해당 위치를 표시한다.
- 트레이너 소개는 별도 페이지로 제공하고 지점별 섹션에 자동으로 묶는다. 트레이너 한 명의 소속 지점은 정확히 하나다.
- 트레이너 정보에는 이름, 소속 지점, 프로필 사진, 한줄소개, 간단한 약력, 직급을 둔다.
- 직급은 선택 입력인 자유 텍스트다. 직급 테이블·별도 관리 메뉴·고정 선택 목록을 만들지 않는다. 미입력 시 표시하지 않고 권한·자동 정렬과 연결하지 않는다.
- 게시글 작성·공개와 팝업 활성화는 별개다. 팝업은 게시글에 선택적으로 연결하며 사용 여부와 시작·종료 일시를 설정한다.
- 운영자는 정해진 화면 안에서 콘텐츠를 수정한다. 섹션 자유 추가·삭제·재배치 및 페이지 빌더는 제공하지 않는다.
- 향후 고객용 프론트엔드와 백엔드를 분리할 계획이다. 운영자 관리 화면을 함께 신규 개발해야 한다는 전제는 두지 않는다.
- Django + Wagtail은 현재 우선 검토 기술안이다. 이 문서는 기술 스택·버전·구체 배포 구성·DB 스키마를 확정하지 않는다.

현재 환경 조건(2026-09-18 갱신): Windows는 호스트·편집/브라우저 접근 환경이며 개발 실행·가상환경·테스트는 WSL Ubuntu 기준이다. 별도 Linux 상용 서버의 배포판·버전·호스팅·실행 방식은 미정이다. `review-resolution.md`의 이전 환경 기록은 보존한다. 승인된 SPIKE-01의 Post·CMS 이미지 격리 시험만 별도 수행하며 전체 구현·정책 승인은 아니다.

## 2. 이번 초안의 화면 구성 제안

아래 경로는 설명을 위한 제안이며 최종 라우팅 계약은 아니다.

| 화면 ID | 화면 | 경로 예시 | 주 역할 |
|---|---|---|---|
| HOME | 홈 | `/` | 브랜드 소개와 주요 정보로의 진입 |
| BRANCH | 지점 안내 | `/branches/` | 지점별 시설·이용안내·지도·상담 연결 |
| TRAINER | 트레이너 소개 | `/trainers/` | 소속 지점별 트레이너 프로필 표시 |
| POST-LIST | 공지·이벤트 | `/posts/` | 공통 게시글 목록 |
| POST-DETAIL | 게시글 상세 | `/posts/{게시글 식별자}/` | 공개 게시글의 본문 제공 |

팝업은 독립적인 고객용 페이지가 아니라 홈에서 게시글로 유도하는 홍보 요소로 제안한다. 관리자 화면의 URL은 기술 설계 단계에서 결정한다.

## 3. 공통 내비게이션과 문의 흐름 — 제안

- 상단 메뉴: 홈 / 지점 안내 / 트레이너 소개 / 공지·이벤트.
- 공통 주요 버튼: ‘지점별 문의’. 공개 지점이 하나면 해당 지점 안내 영역으로, 여러 개면 지점 목록으로 이동한다.
- 각 지점의 전화·카카오톡 버튼은 해당 지점에 저장된 정보를 사용한다. 공통 버튼이 아무 설명 없이 본점에 연결되지는 않는다.
- 전화번호는 읽고 복사할 수 있는 텍스트로도 표시한다.
- 연락처가 등록되지 않은 채널의 버튼은 숨긴다. 지점 공개를 위해 전화·카카오톡 중 최소 하나의 유효한 연락 경로를 요구하는 안을 제안한다.
- 하단의 로고·브랜드명·메뉴는 공통 설정을 사용한다. 지점명·주소·연락처를 보여주는 부분은 지점 데이터를 재사용한다.

## 4. HOME — 홈

### 4.1 고정된 화면 순서 — 제안

1. 대표 사진 + 핵심 소개 문구 + 지점별 문의 버튼.
2. 헬스장 소개: 짧은 설명과 소개 사진.
3. 지점 소개 미리보기: 공개 지점을 자동으로 반복 표시.
4. 트레이너 소개 페이지로 이동하는 안내 영역.
5. 최근 공개 공지·이벤트.
6. 공통 하단 영역.

별도 가격·요금 섹션은 없다. 시설·이용안내의 자세한 내용은 지점 안내로 연결한다. 홈 미리보기용으로 지점을 다시 등록하거나 수동 배치하지 않는다.

### 4.2 운영자 입력과 자동 반영

- 운영자 입력: 대표 사진과 대체 설명, 핵심 소개 제목·문구, 헬스장 소개 문구·사진.
- 지점 미리보기: 지점명, 본점 여부, 대표 사진, 짧은 소개 등 기존 지점 데이터 사용.
- 최근 게시글: 공개된 글을 최근 공개일 순서로 사용. 노출 개수는 화면 상세 설계에서 정한다.
- 트레이너 안내: 별도 페이지로 이동한다. 같은 프로필을 홈용 데이터로 중복 등록하지 않는다.
- 콘텐츠가 없는 자동 영역은 빈 카드나 개발용 예시를 보여주지 않고 숨긴다.

P-01 Proposed: 홈 공통 설정은 별도 수정 초안 없이 유효한 저장 커밋 후 새 조회에 반영한다. 공개 전 검수는 저장 전에 수행하며, 저장을 게시글의 ‘수정 초안 저장’으로 안내하지 않는다.

## 5. BRANCH — 지점 안내

### 5.1 화면 배치 — 제안

v1은 지점별 상세 페이지를 따로 만들지 않고, 지점 안내 페이지 한 곳에서 공개 지점별 소개 영역을 반복한다. 상단 지점 바로가기는 해당 소개 영역으로 이동한다. 지점이 하나일 때 불필요한 선택 절차를 만들지 않는다.

지점 수 증가에 따른 성능·사용성 문제가 확인되면 이후 상세 페이지나 선택형 표시를 검토한다. 이는 v1 추가 범위가 아니다.

### 5.2 지점별 표시 정보

- 지점명, 본점 표시, 짧은 지점 소개, 대표 사진.
- 주소·상세 주소, 외부 지도, 전화·카카오톡 버튼.
- 운영시간, 휴무, 주차 안내, 기타 이용안내.
- 시설 사진 목록 및 필요한 사진 설명.
- ‘이 지점 트레이너 보기’: 트레이너 소개 페이지의 해당 섹션으로 이동.

### 5.3 관리자 입력 — 제안

- 지점명, 본점 여부, 공개 여부, 표시 순서.
- 대표 사진, 짧은 소개.
- 기본 주소·상세 주소, 위치 확인 상태.
- 전화번호, 카카오톡 채널 주소.
- 운영시간, 휴무 안내, 주차 안내, 기타 이용안내.
- 시설 사진 여러 장, 각 사진의 설명·대체 설명·표시 순서.

운영시간은 첫 버전에서 읽기 쉬운 안내 텍스트로 관리한다. 실시간 영업 상태 계산·예약 가능 시간표는 만들지 않는다.

P-01 Proposed: 지점 필드·시설 사진 배치·이용안내는 하나의 부모 편집 저장 단위다. 공개 지점의 유효한 저장은 커밋 후 새 조회에 반영된다. 미완성 신규 입력은 ‘비공개 준비 상태’로 저장하며 기존 공개본을 유지하는 수정 초안 기능은 제공하지 않는 안이다. 사진 업로드 성공만으로 공개하지 않고 부모 저장 실패 시 부분 반영을 막는다.

### 5.4 지도 동작 — 제안

1. 운영자가 기본 주소를 입력한다.
2. 외부 지도 서비스로 위치를 조회한다.
3. 운영자가 검색된 위치를 확인한다.
4. 저장·공개한 지점의 위치를 고객 화면에 표시한다.

주소 변경 시 위치를 재확인하며 이전 주소의 마커를 새 주소와 함께 노출하지 않는다. 위치 검색 실패나 지도 로딩 실패 시 잘못된 마커·임의의 기본 좌표를 보여주지 않는다. 고객은 주소와 연락처를 확인할 수 있고, 운영자에게 위치 확인 필요 상태를 알린다. 상세 주소는 안내용으로 별도 관리한다. 지도 제공자·API 키·좌표 저장 정책·쿼터는 기술 설계에서 검증한다.

### 5.5 자동 표시·공개 규칙 — 제안

- 공개 지점만 표시한다. 본점을 먼저, 나머지를 설정 순서로 표시한다.
- 지점 추가·수정·비공개 변경은 홈 미리보기와 지점 안내에 같은 원본 데이터로 반영한다.
- P-02 Proposed: 최초 준비 중 공개 지점 0개는 허용한다. 첫 지점 공개와 본점 지정은 원자적으로 처리한다. 공개 지점이 있으면 공개 본점이 정확히 하나이며 비공개 지점은 본점이 될 수 없다. 본점 비공개는 다른 공개 본점 지정과 함께 처리한다. 운영 중 마지막 공개 지점의 비공개 전환은 차단하며 전체 종료 기능은 추가하지 않는다.
- 지점에 공개 트레이너가 없다면 ‘이 지점 트레이너 보기’를 숨긴다.
- P-03 Proposed: 일반 운영자의 콘텐츠·원본 이미지 영구 삭제는 서버 권한에서도 차단한다. 일상 운영은 본점 제약을 지킨 비공개 전환으로 처리한다. 시설 사진 배치 제거는 원본 삭제와 구분한다. 유지보수 삭제·복원은 데이터 모델 §11의 참조 검증과 별도 승인 대상이다.

## 6. TRAINER — 트레이너 소개

### 6.1 구성

- 공개 지점을 기준으로 지점별 섹션을 자동 구성한다.
- 각 섹션에 해당 지점의 공개 트레이너 프로필을 반복 표시한다.
- v1에는 트레이너별 개별 상세 페이지를 추가하지 않고 카드에서 사진·이름·직급·한줄소개·간단한 약력을 읽게 하는 안을 제안한다.

### 6.2 관리자 입력 — 제안

- 이름: 필수.
- 소속 지점: 등록된 지점 하나를 필수 선택.
- 직급: 선택 입력인 자유 텍스트.
- 프로필 사진: 공개 전에 준비. P-01 Proposed에 따라 미등록 입력은 ‘비공개 준비 상태’로 저장할 수 있으나 게시글식 수정 초안은 아니다. 가상의 대체 인물 이미지를 생성하지 않는다.
- 한줄소개: 공개용 소개 문구.
- 약력: 학력 / 수상경력 / 자격증 / 주요 경력의 고정 구분에 여러 항목 입력.
- 공개 여부, 지점 내 표시 순서.

약력 구분은 별도 관리 메뉴로 만들지 않는다. 입력 항목이 없는 약력 구분과 미입력 직급은 고객 화면에서 제목·빈 공간까지 숨긴다. 입력 가능 길이와 공개 전 필수 검증의 세부값은 상세 설계에서 확정한다.

P-01 Proposed: 소속·직급·사진 참조·한줄소개·약력은 동일 프로필의 부모 편집 저장 단위다. 공개 상태의 유효한 저장은 함께 반영하며, 수정 중 숨길 필요가 있으면 먼저 비공개로 전환한다. 그동안 기존 소개도 보이지 않는다는 점을 관리자에게 안내한다.

### 6.3 자동 반영 — 제안

- 프로필 자체와 소속 지점이 모두 공개이고 공개 필수 조건을 충족할 때 자동 반영한다. 공개 지점의 첫 공개 트레이너라면 섹션도 자동 생성한다. 비공개 지점에서는 프로필 자체를 공개해도 고객에게 보이지 않는다.
- 소속 변경 시 기존 트레이너 데이터는 유지하고 소속 지점 섹션만 바꾼다.
- 지점명 수정은 섹션 제목에 반영한다.
- 지점은 본점 우선·설정 순서, 트레이너는 지점 내 설정 순서로 표시한다. 직급 문구로 순서를 추론하지 않는다.
- 공개 트레이너가 없는 지점 섹션은 숨긴다.
- 비공개 지점의 트레이너는 공개 페이지에 표시하지 않되, 해당 트레이너의 데이터·자체 공개 설정을 자동 삭제·변경하지 않는다.

## 7. POST-LIST / POST-DETAIL — 공지·이벤트

### 7.1 목록 — 제안

- 전체 / 공지사항 / 이벤트 필터.
- 제목, 분류, 공개일, 선택적 대표 이미지 표시.
- 공개 글만 최근 공개일 순으로 표시하고 글이 늘면 페이지를 나눈다.
- 결과가 없으면 ‘등록된 게시글이 없습니다’라는 상태를 표시한다.
- 검색·태그·댓글·좋아요·고정글은 현재 초안에 추가하지 않는다.

### 7.2 상세 — 제안

- 제목, 분류, 공개일, 본문·본문 이미지, 목록으로 돌아가기.
- 초안·비공개·삭제된 글은 일반 방문자의 직접 주소 접근에서도 읽을 수 없다.
- 운영자 미리보기는 권한이 있는 관리 흐름에서만 제공하고 공개 상태를 변경하지 않는다.
- 가격 전용 필드·화면을 만들지 않으며, 게시글 본문·이미지·팝업 등 모든 공개 콘텐츠에 가격이 포함되지 않도록 공개 전에 사람이 검수한다. 가격 자동 판별·OCR 기능은 v1 범위에 추가하지 않는다. 가격 필드가 없다는 사실만으로 콘텐츠 검수를 통과 처리하지 않는다.

### 7.3 관리자 입력 — 제안

- 분류: 공지사항 또는 이벤트.
- 제목, 선택적 대표 이미지, 서식과 이미지가 가능한 본문.
- 초안 / 공개 / 비공개 상태.
- 공개일: 실제 공개 흐름과 연계하여 관리.
- 게시글과 연결된 선택적 팝업 설정으로 이동 또는 같은 편집 화면에서 관리.

게시글 예약 공개는 현재 명시 요구가 아니므로 v1 기본 범위에 추가하지 않는다. 팝업 기간 예약과 게시글 공개는 구분한다.

P-01 Proposed: Post만 공개본과 수정 초안을 분리한다. 제목·분류·본문·본문 이미지 참조·대표 이미지 참조는 같은 공개 버전이다. 수정 초안 저장은 기존 공개 내용·공개 시각·팝업의 게시글 제목을 바꾸지 않는다. 최초 공개일 유지 정책은 여전히 별도 미확정 제안이다.

## 8. POPUP — 공통 기간제 팝업

### 8.1 확정된 동작

- 공지·이벤트 게시글에 선택적으로 연결한다.
- 게시글 작성·공개만으로 팝업을 자동 활성화하지 않는다.
- 운영자가 팝업 사용 여부와 활성 시작·종료 일시를 지정한다.
- 지점별로 구분하지 않는다.

### 8.2 이번 화면 초안의 제안

- 홈에서만 자동 노출한다. 게시글 상세·트레이너 소개에 진입할 때마다 다시 띄우지 않는다.
- 제목, 안내 문구 또는 이미지, ‘자세히 보기’, 닫기 버튼을 제공한다.
- ‘자세히 보기’는 연결된 공개 게시글로 이동한다.
- 모바일에서는 본문 접근을 막지 않는 작고 닫을 수 있는 안내 형태를 사용한다.
- 사용 가능한 팝업 중 하나만 자동 노출하고 닫은 직후 다른 팝업을 연속 표시하지 않는다.
- 같은 탭의 연속 탐색에서 일반 닫기를 기억하고, 선택적 ‘오늘 하루 보지 않기’는 해당 브라우저·팝업에 대해 한국 시간 다음 날 00:00까지 적용한다.
- 여러 후보의 선택 순서, 숨김을 고려한 후보 선택·대체 노출의 상세 규칙은 구현 전에 명시한다.
- 모달 형태를 택하면 키보드 닫기와 포커스 이동도 검증한다.

위 노출 위치·최대 개수·닫기 기억 정책은 화면 설계 제안이며 사용자 확정 요구사항과 구분한다.

### 8.3 관리자 입력과 판정 — 제안

- 연결 게시글, 표시 제목·문구·이미지, 사용 여부(기본 꺼짐), 시작 일시, 종료 일시, 표시 우선순위.
- 활성화 시 연결 게시글·표시 콘텐츠·유효한 기간을 확인한다. 종료가 시작보다 늦어야 한다.
- 시간 입력·표시는 Asia/Seoul 기준으로 한다.
- 서버의 노출 후보 조건: 연결 글 공개 AND 팝업 활성 AND 시작 <= 현재 < 종료.
- 방문자 닫기·오늘 숨김은 서버가 반환한 공개 가능 후보에 추가로 적용한다. 비공개 콘텐츠를 프론트에서만 숨기지 않는다.
- 기간 만료·팝업 비활성화는 게시글 공개 상태를 바꾸지 않는다. 연결 글 비공개 시 이후 조회에서 팝업도 제외한다.
- 관리자에게 비활성 / 예약 / 노출 가능 / 종료 / 연결 글 비공개로 중지 상태를 보여준다. 방문자별 실제 노출과 서버의 노출 가능 상태를 구분한다.
- 이미 열려 있는 화면을 운영자가 실시간 원격 회수하는 기능은 v1 기본 범위에 넣지 않는다. 종료 이후 새 조회와 캐시 결과에서는 제외되어야 한다.

P-01 Proposed: 팝업은 게시글식 수정 초안 없이 연결 글·문구·이미지 참조·기간·사용 여부를 함께 저장한다. 활성 기간 중 유효한 변경은 커밋 후 후보 조회에 반영되므로 저장 전에 수동 공개 검수를 한다. 방문자의 닫기·오늘 숨김은 이 저장/공개 판정과 독립이다.

## 9. 운영자 관리 화면 구성 — 제안

| 관리 영역 | 관리 대상 |
|---|---|
| 홈페이지 기본 정보 | 브랜드명·로고, 홈 소개 문구·사진 |
| 지점 | 지점 기본 정보, 시설 사진, 이용안내, 연락처·지도, 본점·공개·순서 |
| 트레이너 | 소속 지점, 이름·직급·사진·한줄소개·약력, 공개·순서 |
| 공지·이벤트 | 게시글 작성·편집·공개·비공개 |
| 팝업 | 연결 글, 표시 콘텐츠, 사용 여부·기간·우선순위 |

시설·이용안내는 지점 편집에, 약력은 트레이너 편집에 포함한다. 직급·지점별 게시판·가격·PT 운영 기능용 메뉴를 추가하지 않는다. 팝업 관리와 게시글 편집의 연결 방식은 선택한 CMS의 기존 관리 화면 안에서 구성한다. 자유로운 레이아웃 편집기는 만들지 않는다.

P-03~04 Proposed: 이미지 교체는 기존 바이너리 덮어쓰기 대신 새 자산 참조로 한다. 초안 전용 원본·관리자 썸네일·변환본은 권한 있는 관리 경로로만 제공하고 공개 API의 범위를 넓히지 않는다. 공개 사용처가 있는 공유 이미지 표시본은 공개될 수 있으므로 미공개 독점 자료에는 새 자산을 쓴다. 영구 삭제 차단·권한 있는 미리보기·게시글 리비전 복원 후 재검증을 기존 CMS 안의 최소 연동으로 검증한다. 상세 조건은 데이터 모델 §11과 ADR-0002를 따른다.

## 10. 향후 프론트 분리를 고려한 설계 원칙

- 홈페이지 전체를 하나의 자유 HTML 덩어리로 저장하지 않는다. 문구·사진·지점·프로필·게시글·팝업의 역할을 구분한다.
- 지점·트레이너·게시글의 공개 조회와 팝업 기간 판정은 백엔드에서 일관되게 처리한다.
- 초기 화면과 향후 API가 같은 공개 규칙과 데이터를 사용한다.
- 직급 표시·레이아웃·모바일 배치 등 표현과 콘텐츠 공개 정책을 구분한다.
- API에는 고객 화면에 필요한 공개 데이터만 제공한다. 관리용 필드·초안·비공개 항목을 그대로 내보내지 않는다.
- 이미지 주소·대체 설명과 본문 내부 이미지·링크를 별도 프론트에서도 사용할 수 있도록 추후 API 계약에서 정의한다.
- 정확한 API 경로·응답 스키마·DB 종류·인증·미디어 저장소·캐시·배포 방식은 후속 기술 설계 대상이다.

운영 이미지 URL은 절대 HTTPS를 사용하고, 로컬 개발만 명시된 HTTP 개발 오리진 예외를 허용하는 안이다. 운영 설정에 예외를 넘기지 않는다. Windows/Linux 차이는 ADR-0001의 ENV-01~06으로 검증한다.

## 12. 다음 단계와 미결정 사항

- 우선 화면 구성 제안을 검토하고 수정한다. 홈 섹션 순서, 지점 한 페이지 구성, 팝업 자동 노출 위치·닫기 정책 등은 확정 요구와 구분한다.
- 다음으로 콘텐츠 모델·공개 API 계약·기술 선택을 설계한다. 이 단계에서도 PT 관리 시스템의 데이터 구조·계정·기능을 가져오지 않는다.
- 브랜드명·로고·실제 지점 정보·사진·트레이너 약력 등 실콘텐츠는 제공 전까지 TBD로 둔다. 정보가 없다는 이유로 예시를 사실처럼 공개하지 않는다.
- 파일 경로 권장안: `docs/screens.md`. 기존 저장소에 같은 역할의 문서가 있다면 확인 후 중복 문서 대신 그 구조를 따른다.
- 이 초안만으로 코드 구현을 자동 시작하지 않는다. 후속 구현 작업에는 승인 범위와 완료 조건을 별도로 지정한다.
