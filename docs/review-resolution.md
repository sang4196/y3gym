## 1. 이 문서의 지위

사용자가 공유한 Codex 정합성 검토 보고와 대화에 첨부된 세 원본 명세를 바탕으로 작성했다. 사용자의 로컬 저장소를 직접 확인·수정한 결과가 아니다. 검토 보고는 구현 결함이나 테스트 통과를 입증하지 않는다.

이번에 사용자가 추가한 확정 조건은 **현재 Windows 기반 개발 환경, 향후 Linux 상용 서버 배포**다. Windows 제품 종류·버전, Python·DB·Docker·WSL 설치 여부, 운영 호스팅은 확인되지 않았다. ‘Windows 개발 서버’라는 표현을 Windows Server 제품군이라는 뜻으로 단정하지 않는다.

아래 항목을 구분한다.

- **C: 기존 확정 요구와 문구 정정** — 새로운 기능 승인이 아니라 기존 의미의 명확화다.
- **P: 신규 운영 정책 제안** — 이 문서를 저장하거나 Codex가 수정 문서에 반영해도 사용자 승인으로 승격하지 않는다.
- **A: 아키텍처 권고안** — 실제 설치·버전 고정·운영 배포는 별도 구현 작업에서 수행한다.

Django + Wagtail, PostgreSQL, 초기 템플릿, 개발용 실행 방식은 여전히 권고안이다. 기존 미확정 화면 배치·팝업 개수·노출 위치·닫기 정책·API 경로 등을 이 문서로 일괄 승인하지 않는다.

## 2. 보존할 제품 범위

하나의 헬스장 홍보·정보 제공 홈페이지다. 가격은 공개하지 않으며 PT 관리 서비스와 절대 연계하지 않는다. 고객 로그인·예약·결제·지점별 게시판·트레이너 업무 계정·자유로운 페이지 빌더·별도 관리자 프론트는 추가하지 않는다.

본점과 지점은 같은 구조이며 운영자가 공개한 지점은 홈과 지점 안내에 자동 반영한다. 시설·이용안내는 지점별이다. 트레이너는 지점 하나에만 소속되며 직급은 선택 자유 텍스트다. 직급은 권한·자동 정렬과 무관하다. 게시글·팝업은 공통이다. 팝업의 사용 설정과 활성 기간은 게시글 공개와 독립이다.

## 3. C — 바로 명확히 할 문구와 검증 조건

### C-01 가격 비공개

기존 screens §7.2의 모호한 문구를 다음 의미로 바꾼다.

> 가격 전용 필드·화면을 만들지 않으며, 게시글 본문·이미지·팝업 등 모든 공개 콘텐츠에도 가격이 포함되지 않도록 공개 전에 사람이 검수한다. 가격 자동 판별·OCR 기능은 v1 범위에 추가하지 않는다.

API 필드 검사와 실제 콘텐츠 검수를 분리한다. 응답에 `price`라는 필드가 없다는 사실만으로 UX-18을 통과 처리하지 않는다.

### C-02 UX-06

프로필 자체와 소속 지점이 모두 공개이고 공개 필수 조건을 충족한 트레이너가 공개 조회에 자동 등장한다. 비공개 지점의 프로필 자체를 공개해도 고객에게는 보이지 않는다.

### C-03 UX-10

지점 비공개는 본점·관계 제약을 통과한 변경에 한해 적용한다. 비공개 성공 시 홈·지점 안내·해당 트레이너 섹션에서 제외하되 데이터와 트레이너 자체 공개 설정을 유지한다. 본점 비공개 허용 전제는 P-02와 함께 명시한다.

### C-04 UX-16

‘관리자 콘텐츠 변경’ 대신 ‘해당 모델의 공개 반영 규칙에 따라 커밋된 변경’으로 표현한다. 게시글 수정 초안 저장은 공개 반영에 해당하지 않는다. 반영 시점의 모델별 차이는 P-01에서 제안한다.

### C-05 직접 추적 보강

기존 UX/API 식별자는 보존한다. 추가 검증 항목은 새 ID를 부여하고 다음을 독립적으로 추적한다.

- 시설 사진의 부모 지점 소유권·순서 변경 및 다른 지점에 미치는 영향 없음.
- 공개 지점의 첫 공개 트레이너 등록 시 섹션 자동 생성.
- 직급 텍스트 변경 전후 관리자 권한·정렬 순서 불변.
- 모델별 저장/공개 시점, 본점 비공개 전제, 미디어 접근은 각각 독립 테스트다.

이들은 테스트 계획이며 현재 통과 결과가 아니다.

## 4. P-01 — 모델별 저장·공개 정책 제안

모든 콘텐츠에 다중 공개 버전과 수정 초안을 도입하지 않는다. v1은 **게시글만 공개본과 수정 초안을 분리**하고, 그 외 소개·설정은 단일 현재값으로 관리한다.

| 대상 | 편집 방식 | 공개 반영 단위 |
|---|---|---|
| SiteContent | 별도 수정 초안 없이 저장 | 유효한 사이트 설정 저장 커밋 후 새 조회 |
| Branch | 공개/비공개와 별개로 단일 현재값 저장 | 지점 필드·시설 사진·이용안내를 부모 편집 작업 단위로 함께 저장 |
| Trainer | 공개/비공개와 별개로 단일 현재값 저장 | 소속·직급·사진 참조·한줄소개·약력을 함께 저장 |
| Post | 초안 저장 / 공개 / 비공개를 구분 | 제목·분류·본문·본문 이미지 참조·대표 이미지 참조를 같은 공개 버전으로 취급 |
| Popup | 사용 설정·기간을 가진 현재 설정 저장 | 연결 글·문구·이미지 참조·기간·사용 여부를 함께 저장; 이후 후보 조회에서 판정 |

공개 지점·트레이너의 변경은 유효한 저장이 성공하면 반영된다. 수정 중 내용을 별도로 보관하고 싶으면 먼저 비공개로 전환할 수 있으나 그동안 고객에게 소개가 보이지 않는다는 점을 관리자에게 안내한다. 이를 ‘기존 공개본이 유지되는 수정 초안’으로 설명하지 않는다.

새 지점·트레이너의 미완성 입력은 비공개로 저장할 수 있다. 문서에서 이 상태를 부를 때는 ‘비공개 준비 상태’라고 하고 게시글의 ‘공개본과 공존하는 수정 초안’과 구분한다.

시설 사진 배치와 약력 항목은 부모 편집 작업과 같은 DB 트랜잭션으로 저장한다. 부모만 저장되고 하위 항목 일부만 반영된 상태를 허용하지 않는다. 이미지 바이너리 업로드는 DB 트랜잭션과 동일하다고 가정하지 않는다. 업로드 후 부모 저장이 실패한 파일은 미참조·미공개 상태로 남을 수 있으며 자동 공개하지 않는다.

본점 변경·트레이너 소속 변경·팝업 설정 변경에는 게시글식 수정 리비전을 적용하지 않는다. 수정 이력 기록이 있더라도 그것을 별도의 공개 대기본으로 오해하지 않는다.

Post의 공개본과 수정 초안은 CMS 기능을 재사용한다. 다단계 승인·예약 게시글 공개는 추가하지 않는다. 수정 초안 저장은 공개일·공개 updated_at·팝업이 사용하는 게시글 제목을 바꾸지 않는다. 새 수정본 공개 시만 반영한다. 최초 공개일 유지 정책은 기존 미확정 제안으로 남긴다.

본문은 허용된 서식과 이미지·안전한 링크만 사용한다. 별도 초안 객체의 내용을 참조하여 공개 본문이 우회 변경되는 동적 임베드는 v1에서 추가하지 않는다. 공개 조회는 CMS 내부 최신 리비전이 아니라 실제 공개본을 사용한다. [S1]

### P-01의 대가

지점·트레이너 수정 중 기존 공개본을 유지하는 미리보기/초안 기능은 제공하지 않는다. 이를 나중에 추가하려면 관계·사진·약력까지 묶인 공개 버전 정책을 별도 변경한다. 현재는 운영 단순성과 공개 시점 명확성을 우선하는 제안이다.

## 5. P-02 — 본점·전체 비공개 정책 제안

1. 최초 준비 단계에서 공개 지점 0개는 허용한다. 비공개 준비 지점은 여러 개 있어도 된다.
2. 첫 지점 공개는 그 지점을 본점으로 지정하는 작업과 원자적으로 처리한다.
3. 공개 지점이 하나 이상이면 공개된 본점이 정확히 하나여야 한다. 비공개 지점을 본점으로 지정하지 않는다.
4. 현재 본점을 비공개로 바꾸려면 다른 공개 지점을 본점으로 변경하는 작업을 함께 완료해야 한다.
5. 마지막 공개 지점을 비공개로 바꿔 공개 지점이 0개가 되는 일반 편집 작업은 차단한다. v1에는 ‘전체 영업 종료/사이트 전체 공개 중단’ 기능을 추가하지 않는다.
6. 중복 본점 방지와 본점 존재 보장은 별도로 검증한다. 동시 본점 변경에서도 중간 상태가 남지 않게 처리한다. 구체 잠금·제약 구현은 ADR 대상이다.

최초 0개 상태를 허용하는 것과 운영 중 양수에서 0개로 바꾸는 것을 같은 동작으로 취급하지 않는다. 이 규칙을 위해 별도 사이트 종료 기능을 만들어 범위를 키우지 않는다.

## 6. P-03 — 삭제·이미지 교체·복원 정책 제안

일반 콘텐츠 운영자에게는 지점·트레이너·게시글·팝업·원본 이미지의 영구 삭제 권한을 제공하지 않는 안이다. 서버 권한에서도 차단하며 버튼만 숨기지 않는다. 일상 운영은 비공개·팝업 비활성화로 처리한다.

시설 사진의 배치 제거와 약력 한 줄 제거는 허용한다. 이는 부모에 포함된 콘텐츠 편집이며 공유 이미지 파일의 삭제와 다르다.

이미지의 바이너리를 기존 자산 ID·URL에 덮어쓰지 않는다. 교체할 때는 새 자산으로 업로드하고 부모의 참조를 바꾼다. 기존 게시글 공개본·수정 초안·보존 중 리비전이 참조하는 원본은 유지한다. 이미지의 시각적 내용이 바뀌면 새 자산을 사용한다. 사용 위치별 캡션·대체 텍스트는 해당 콘텐츠에서 관리한다.

정리용 일괄 삭제 화면·자동 미참조 자산 삭제·자동 리비전 청소는 v1에 추가하지 않는다. 실제 시스템 유지보수 삭제가 필요해질 때는 공개본·현재 비공개 객체·수정 초안·보존된 모든 리비전의 참조를 검사하는 별도 승인 작업으로 수행한다. CMS 참조 인덱스가 이 범위를 전부 처리한다고 사전 검증 없이 가정하지 않는다.

CMS가 제공하는 게시글 과거 리비전 복원을 사용하는 경우, 복원은 먼저 수정 초안으로 만들고 재검증 후 공개한다. 이미지 존재·관계 유효성·공개 가능성을 다시 검사한다. 유실된 파일을 가짜 경로나 임의 사진으로 대체하지 않는다. 필수 이미지가 없는 새 공개는 막고, 실제 스토리지 유실은 오류 보고·백업 복구 대상으로 처리한다. v1에서 복원 기능을 제공하지 않는 모델에 신규 범용 복원 기능을 만들지는 않는다.

시스템 최고 권한·DB 직접 조작까지 불가능하다고 보장하는 정책은 아니다. 운영자 일상 권한과 유지보수 권한을 구분한다.

## 7. P-04 — 미공개 미디어 접근 보호 제안

### 목표

글을 비공개로 설정하는 것과 이미지 파일을 비공개로 보호하는 것은 별개다. **한 번도 공개하지 않은 파일을 URL만 알면 볼 수 있는 상태는 기본 허용하지 않는 안**을 권고한다. 사진·본문·팝업 이미지에 동일하게 적용한다.

Wagtail의 컬렉션 privacy 설정은 문서에 적용되지만 이미지에는 적용되지 않는다. 따라서 기본 CMS만 설치하면 이 정책을 만족한다고 보고해서는 안 된다. [S2]

### 최소 접근 규칙

- 업로드 원본은 비공개 저장소 또는 웹 서버에서 직접 제공하지 않는 경로에 둔다.
- 원본·관리자 썸네일·미공개용 변환 이미지에는 권한 있는 운영자만 접근한다. 관리 화면 미리보기는 인증된 관리 경로로 제공하며 공개 API를 확장하지 않는다.
- 일반 방문자에게는 현재 공개 콘텐츠가 사용하는 표시용 이미지/변환본만 허용한다. 이미지 목록 전체를 공개하는 별도 API를 추가하지 않는다.
- 주소 추측·긴 무작위 파일명·디렉터리 목록 숨김은 인증·인가를 대신하지 않는다.
- 웹 서버 직접 경로, 객체 저장소 원본 URL, 원본 미디어 URL, 변환본 URL 중 하나라도 우회 접근이 가능하면 보호를 통과한 것이 아니다.
- 공유 이미지는 공개 사용처가 하나라도 있으면 그 공개 표시본을 숨길 수 없다. 미공개 독점 자료를 만들 때는 기존 공개 이미지가 아니라 새 자산을 사용한다.
- 공개 사용처가 모두 사라진 이미지는 이후 원본 서버의 무권한 조회에서 제공하지 않는 안이다. 이미 내려받은 파일과 방문자·외부 캐시에 남은 과거 공개 복사본까지 회수하는 것은 보장하지 않는다.
- 미리보기·보호 이미지 응답은 캐시하지 않는다. 공개 이미지의 캐시 정책은 콘텐츠 JSON과 분리하되 v1에서 장기 공개 CDN 캐시를 자동 도입하지 않는다.

구현 후보는 비공개 저장소 + 권한을 확인하는 전달 경로다. 스토리지 종류·서명 URL·웹 서버 내부 전달 기능·Wagtail 이미지 URL 연결 방식은 ADR의 작은 기술 검증으로 선택한다. 이미지마다 사용 범위를 판정할 때 지점 공개, 트레이너와 지점의 동시 공개, 게시글의 실제 공개본, 팝업 활성 기간을 사용한다. 이 판정은 콘텐츠의 공통 공개 규칙을 재사용한다.

이 기능은 관리자 페이지 전체를 새로 만드는 일이 아니라 저장·전달 계층의 연동이다. 그러나 구현 작업이 전혀 없다는 뜻도 아니다. 운영자가 ‘홍보용 이미지는 업로드 즉시 URL 접근이 가능해도 된다’고 명시적으로 승인하면 더 단순한 정책으로 바꿀 수 있지만, 승인 없이 그 예외를 적용하지 않는다.

## 8. A-01 — Windows 개발 / Linux 운영 아키텍처 권고

### 확정과 제안

확정: 현재 Windows 개발, 향후 Linux 상용 배포, 추후 고객 프론트 분리.  
제안: Django + Wagtail + PostgreSQL, 초기 서버 템플릿, 하나의 애플리케이션·DB, 재사용 가능한 공개 조회 로직.

| 영역 | Windows 개발 기준안 | Linux 운영 기준안 |
|---|---|---|
| 애플리케이션 | 같은 소스 코드, Windows용 독립 가상환경 | 같은 소스 코드, Linux에서 의존성 재설치 또는 Linux 이미지 빌드 |
| 실행 서버 | 로컬·제한된 개발망의 Django 개발 서버 | 운영용 WSGI/ASGI 서버; Gunicorn을 우선 검토 |
| 웹 진입 | 로컬 개발 주소 | HTTPS 리버스 프록시 및 운영 호스트 검증 |
| DB | 별도 개발 PostgreSQL | 별도 운영 PostgreSQL; 같은 지원 메이저 계열 우선 |
| 설정 | 개발 설정·개발용 비밀값 | DEBUG=False, 운영 전용 키·DB·미디어 저장소 |
| 파일 | 개발 전용 미디어 저장소 | 배포 디렉터리 밖의 영속 저장소와 백업 |
| 검증 | Windows 실행·관리자 입력 확인 | 초기부터 Linux 통합 검증; 최종 배포 전 운영 설정 스모크 테스트 |

Django는 Windows 개발 설치 절차를 제공한다. Gunicorn은 Unix 계열용 서버이므로 Windows 네이티브 실행의 전제로 두지 않는다. `runserver`는 운영 배포 서버로 사용하지 않는다. [S3][S4][S5]

### Docker / WSL

Windows를 지금 변경하거나 저장소를 이동할 필요는 없다. WSL2/Linux 컨테이너를 이용할 수 있으면 Linux 실행 검증 수단으로 권고할 수 있으나 설치·사용 가능 상태로 단정하지 않는다. Windows Server 제품군이라면 Docker Desktop을 지원 설치 경로로 안내하지 않는다. 실제 OS·가상화·권한 조건은 환경 준비 작업에서 확인한다. Docker/WSL 설치, OS 기능 활성화, 저장소 이동은 현재 문서 작업에 포함하지 않는다. [S6]

컨테이너를 채택할 때도 운영 DB와 미디어는 임시 컨테이너 쓰기 계층에 넣지 않는다. 복잡한 오케스트레이션, Kubernetes, Redis, 메시지 큐는 현재 요구사항 때문에 필요해진 기능이 아니므로 자동 추가하지 않는다.

### 운영체제 차이와 검증 규칙

- 파일 경로는 OS 독립적인 경로 API로 처리한다. `C:\...`나 `/home/개인계정/...` 같은 머신 경로를 앱 코드에 고정하지 않는다. URL 생성과 파일 경로 처리는 분리한다.
- 파일명·import·템플릿·정적 자산의 대소문자를 일치시키고 Linux에서 확인한다. `Logo.png`와 `logo.png`를 같은 파일이라고 가정하지 않는다.
- 실행 안내는 PowerShell과 Linux 셸을 구분한다. Windows에서 Bash 도구나 Make 설치를 당연하게 가정하지 않는다. Linux 셸 파일은 LF, 소스·문서는 UTF-8을 기준으로 검증한다.
- `.venv`, Windows 바이너리, 로컬 의존성 디렉터리를 Linux로 복사하지 않는다. Python 가상환경은 이식 가능한 배포물로 취급하지 않는다. [S7]
- Python·Django·Wagtail·이미지 처리 의존성의 실제 호환 조합을 선택 버전의 공식 문서로 확인하고 잠근다. 현재 설치 사실이나 패키지 최신 버전을 추정하지 않는다. 개발·운영의 OS별 의존성 차이는 명시한다.
- SQL·잠금·본점 무결성의 완료 검증은 PostgreSQL에서 한다. SQLite 기반 확인만으로 동일한 동시성 보장을 주장하지 않는다. Django 문서상 SQLite에서는 `select_for_update()`가 효과를 내지 않는다. [S8]
- 시간은 timezone-aware로 처리하며 표시는 Asia/Seoul, 내부 판정·API 시각은 일관된 UTC 기준을 유지한다. Windows를 포함한 교차 환경을 위해 `tzdata` 의존성을 명시하는 안을 권고한다. OS의 현재 시간대 설정에 팝업 정책을 맡기지 않는다. [S9]
- 운영에서는 절대 HTTPS 미디어 URL을 제공한다. 로컬 개발에서는 명시된 개발 오리진의 HTTP URL을 허용할 수 있다. 이 예외를 운영 설정에 적용하지 않는다. 기존 API §2.2의 무조건 HTTPS 문구에 환경 범위를 보완한다.
- DEBUG·호스트·CSRF·쿠키·비밀키·로그 정책은 개발/운영을 분리한다. 개발 서버의 인터넷 노출을 운영 배포로 취급하지 않는다. 비밀값을 커밋하거나 로그에 출력하지 않는다. [S5]
- 공개 HTML과 향후 JSON API가 같은 공개 조회·변환을 사용한다. 초기에 불필요한 내부 HTTP 호출이나 관리자 프론트 재구현을 추가하지 않는다.

### 데이터와 배포

개발 DB는 테스트 데이터, 운영 DB는 실제 운영 콘텐츠로 분리한다. 동일한 마이그레이션을 적용하되 매 배포마다 개발 DB로 운영 DB를 덮어쓰지 않는다. 최초에 개발 환경에서 작성한 실제 자료를 넘길 필요가 생기면 별도의 선별 이관·검수 작업으로 다룬다.

배포물과 업로드 미디어를 구분한다. static 수집 결과는 재생성 가능하지만 운영 업로드 사진은 유지·백업 대상이다. DB 백업과 미디어 백업을 함께 설계하고 복원 검증을 한다. 배포 시 스키마 변경·백업·운영 점검은 명시된 실행 순서와 승인으로 수행하며, 프로세스 시작마다 임의 스키마 변경을 수행하지 않는다.

향후 프론트를 분리해도 운영 CMS·DB·공개 정책을 유지한다. 프론트의 사전 렌더링·캐시가 콘텐츠 수정이나 팝업 기간을 고정하지 않도록 새 요청의 반영 조건을 계속 검증한다.

## 10. 다음 Codex 작업의 범위

기존 세 문서의 관련 절을 수정하되 확정 요구, 기존 제안, 이 문서의 신규 P/A 제안을 구분한다. Proposed 정책을 Accepted로 승격하지 않는다. 사용자 승인 전에도 구체적인 검토용 정책으로 문서화할 수 있지만 구현 기준 확정으로 보고하지 않는다.

작성할 ADR 권장안:

- `docs/adr/0001-runtime-and-deployment.md`: Windows 개발·Linux 운영, CMS/DB 권고, 버전 선정 기준, 초기 템플릿·향후 API, 검증·배포 경계.
- `docs/adr/0002-publication-and-media.md`: P-01~04, 하위 항목의 저장 단위, 본점·관계 제약, 미디어·삭제·복원 경계.

각 ADR은 Proposed 상태에서 배경·권고 결정·대안·장단점·검증 조건·승인 미정 항목을 적는다. 기술 조합을 사실상 채택·설치한 것처럼 적지 않는다.

프로젝트 루트 `AGENTS.md`는 작업 규칙과 문서 안내만 짧게 작성한다. 현재 단계는 설계이며 코드 구현은 별도 작업 승인이 필요하다고 명시한다. 파일이 없다는 기존 보고를 맹신하지 말고 작업 시 현재 경로의 실제 적용 지침을 다시 확인한다. 미래의 승인된 구현까지 영구 금지하는 표현은 사용하지 않는다. Codex는 시작 시 AGENTS.md 지침을 읽으므로 작성 후 적용 여부를 새 작업에서 확인한다. [S10]

README는 문서 위치·현재 단계·개발/운영 OS를 안내한다. 아직 없는 설치 명령이나 테스트 명령을 실행 가능한 절차로 꾸며 넣지 않는다.

실제 코드, 의존성, 가상환경, Docker/WSL, 운영 설정, CI 워크플로, 마이그레이션, DB, 배포, 커밋·푸시는 이번 문서 작업에서 변경하지 않는다.
